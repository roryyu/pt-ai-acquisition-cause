## 三、波次②：数据源平等改造（含同名指标遮蔽 bug 修复）

### 3.1 问题诊断：同名指标遮蔽 bug

`Adjust` 真实数据入库后，`data.adjust_daily_metrics` 与既有 `data.channel_daily_metrics` **出现了同名指标**（如 `impressions`、`clicks`、`installs`）。原算子指标目录 `operatorMetricCatalog` 按裸 `id` 建索引、**同名"保留首个"**，导致：

- 后入库数据源的同名指标被**静默遮蔽**，永远无法被算子寻址
- 分析结果偏向"恰好排在前面"的数据源，违背"平等分析"原则

### 3.2 方案：目录全局唯一 key（三级消歧）

改造 `lib/server/operators/data-operators.ts`，为 `OperatorMetricEntry` 引入**全局唯一可寻址 `key`**：

```
① 裸 id 在全部数据源中唯一 → key = id（如 installs 仅一处时保持 "installs"）
② 跨模型同名               → key = 表名限定（channel_daily_metrics.impressions / adjust_daily_metrics.impressions）
③ 表名限定后仍冲突（极端）  → key = modelId 限定，兜底保证唯一
```

- `resolveMetricEntry`：**精确匹配 key 优先**；裸 id 命中多个数据源时**返回明确错误并列出各限定 id**（`指标 impressions 存在于多个数据源，请用限定 id 指定其一：…`），**不静默偏向任一源**；完全无命中报"未知指标"
- 算子 `metric` 入参、目录展示、UI 枚举统一改用 `key`；`ALL_METRIC_IDS` / `TIME_METRIC_IDS` 同步

### 3.3 提示词平级化（`lib/server/agents/prompts.ts`）

DataAnalystWorker 提示词彻底去除"本地表优先、外部 API 补充"的层级措辞：

- 数据字典标题改为 **「统一数据集合 · 各数据源平等」**，明确"各表来自不同数据源（BI 中间表同步、外部 API 查询后入库等），共同构成一个统一数据集合，平等对待、无主次优先级"
- 新增规则 **「数据源平等、据实给结论」**：所有数据源地位平等，按问题需要自由组合取用，支撑不足时说明数据边界，不偏向任一来源
- `dataAnalystExternalSourcesBlock` 改为「**与数据字典中的表平等**」；`api_fetch` 描述为"取回后与其他数据平等参与分析"

## 四、波次③：物理 Schema `demo` → `data` 重命名

将 PostgreSQL 物理 schema `demo` 重命名为 `data`，覆盖六个层面，**代码层零残留**。

### 4.1 数据库迁移（事务内，无损）

```sql
ALTER SCHEMA demo RENAME TO data;                              -- 7 表整体迁移，12,371 行数据无损
UPDATE cause.semantic_models SET table_ref = 'data.adjust_daily_metrics'
  WHERE table_ref = 'demo.adjust_daily_metrics';               -- DB 自定义模型挂载同步
```

实测复核：`demo` schema 已不存在，`data` 存在且 7 表齐全；`cause.semantic_models` 唯一挂载 `semantic_model_adjust_daily → data.adjust_daily_metrics`。

### 4.2 六层代码改动

| 层 | 文件 | 关键改动 |
|---|---|---|
| 语义层 | `semantic-query.ts` / `model-store.ts` | 5 个种子模型 `schema: "data"`；`recordToModelDef` 默认 fallback `"data"` |
| 连接器 | `postgres.ts` / `datasources.ts` | `introspectSchema` 默认业务 schema 列表 `["data","cause","public"]` |
