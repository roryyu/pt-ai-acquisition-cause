1. 部署结论与申请原则

  • 新增 1 台 Cause 专用 EC2，同时部署 Cause 应用与 PostgreSQL 17，与 AI Core、Platform 同 VPC 私网部署；运行一个 Web/API 进程、一个数据库实例及受控单次同步 / 备份作业，不部署模型推理或 GPU 服务。
  • 外部必需依赖为 Foundation Gateway 和 Access 统一认证。Access 认证链路包含 Identity 的 OIDC 登录及 Access Internal API 的入口授权 / 会话复核，二者均须可达。复用现有 Internal ALB、告警通道和管理通道，不在 Cause 主机重复部署 Foundation 或 Access。原 RDS 的实例规格、容量、五个逻辑库及安全组访问范围保持不变。
  • Cause 与 Creative / Portal 是平级应用。Creative / Portal 不作为 Cause 的启动依赖，不新增其数据库访问权限；Portal 仅需登记 Cause 入口链接及可见权限。
  • 模型调用消耗 Foundation 配额；分析查询消耗 Cause 本机 PostgreSQL 的 CPU、内存与磁盘 I/O。Cause 应用与数据库不再与 Creative / Portal 争抢数据库资源，但二者共享一台 EC2 的容量和故障域；整机故障会同时中断 Web 与数据库服务。
  • 正式持久化目标：业务及分析数据进入同机 PostgreSQL，PGDATA、导出图片及图谱分别落加密 EBS 数据盘的隔离目录；备份采用本地一致性逻辑备份 + 加密 EBS 快照建议方案。Cause 不新增或复用 S3 Bucket，不要求 S3 适配；原三个 Bucket 继续服务原应用，本次不调整。文件授权下载、容量与恢复验收仍必须完成。
  • 当前按单 Web 进程、单调度执行器部署。单实例仍需限制并发图谱写入；在解决任务锁、文件状态和恢复机制前，不开启多副本、PM2 cluster 或 Auto Scaling。

原第 10 节调整：仍不申请第二环境、高可用副本或第二台 Cause 数据库服务器。本次新增的是 Cause 应用与数据库合一节点，不是原有 AI Core / Platform 的第二套；不再保留 Cause 与 AI Core 合部署的备选方案。全平台为 3 台 EC2 + 原有 1 个 RDS，其中 Cause 使用新增 EC2 上的自管 PostgreSQL。

5. 同机 PostgreSQL、权限和 TLS

5.1 库与 schema

在 Cause EC2 的 PostgreSQL 17 容器内创建 pt_ai_cause，与应用同机但使用独立进程、账号及持久目录。原 RDS 的 pt_ai_access、pt_ai_keycloak、pt_ai_portal、pt_ai_foundation、pt_ai_creative 不变；Cause 不连接这些数据库。

对象内容 / 管理方式
pt_ai_cause.cause用户、本地业务角色、OIDC 事务、会话、数据源、指标、语义模型、问答、研究、画布、定时任务等 Prisma 模型；Prisma datasource.schemas 当前仅包含 cause。
pt_ai_cause.dataAdjust 与 API 取数形成的分析表；当前在应用中通过原生 SQL 使用，不在 Prisma schema 的管理范围内，必须另纳入版本化迁移。
pgvector原开发环境使用带 pgvector 的 PG17 镜像，但当前 Prisma schema 没有 vector 字段。生产可采用通过安全审核且支持 ARM64 的固定版本 PG17 镜像；若保留 pgvector，固定扩展版本并验证恢复兼容。只有启用向量功能时才由迁移 / DBA 创建 vector 扩展，不另申请向量数据库服务。

5.2 角色与连接隔离

  • 新增 pt_ai_cause_runtime 与 pt_ai_cause_migration。Runtime 仅对本应用库拥有 CONNECT、两个 schema 的 USAGE、所需表 DML / 序列权限；Migration 负责受控 DDL，不给 Web 进程持有。核对未来对象的默认权限与对象所有者。
  • PostgreSQL 管理员账号仅用于初始化和批准的运维，不用于应用或同步。默认不允许外部 BI 直连本机数据库；后续确需开放时另批专用 TLS 网络路径和只读角色，仅授权指定 data 表 / 视图。
  • 审计本机 PostgreSQL 的 PUBLIC 默认权限及 Runtime / Migration 所有权，不授权其他平台数据库，也不复用原 RDS 凭据。数据库使用专用 Docker bridge 后端网络，仅接入应用与受控作业，无宿主机端口映射。数据库备份写本地隔离目录，PG 容器无需 S3 或公网出站；Web 另接受控出网网络以访问 Foundation Gateway、Access 认证及获批业务源。快照 API 与运维身份由受控自动化使用，不交给 Web。
  • 本机连接预算包含 Prisma 池、每目标库最多 3 连接的 pg 分析池、同步 CLI、迁移和监控，不包含其他五个应用；首期 max_connections 建议 80 并为运维预留连接，须先核对各池总上限。分析查询初始 statement_timeout 30 秒，长迁移另设受控参数；不要虚构应用已有的连接池环境变量。
  • 自管 PostgreSQL 不继承 RDS 自动备份、PITR、Deletion Protection、自动补丁或托管监控。由 DBA / 运维负责版本升级、备份归档、恢复演练、证书轮换与容量；原 RDS 的这些配置继续服务原有应用。

5.3 TLS 与迁移的阻断项

即使同机，容器间 TCP 连接仍启用 PostgreSQL TLS 和 sslmode=verify-full。通过公司批准 CA 签发数据库证书，SAN 覆盖服务名 postgres，只读挂载证书 / 私钥并设置严格权限；客户端挂载对应 CA bundle，不再使用 RDS CA。服务端 ssl=on，pg_hba.conf 仅允许指定数据库 / 角色 / 后端网段的 hostssl + scram-sha-256，移除开发 trust 及非 TLS 放行规则。Runtime 示例仅表达参数形态：

postgresql://<runtime-user>:<URL编码密码>@postgres:5432/pt_ai_cause?schema=cause&sslmode=verify-full&sslrootcert=/run/certs/cause-pg-ca.pem

postgres 仅在专用容器网络内解析；迁移、CLI 与连接测试也要加入该网络，不能在应用容器中以 localhost 指代另一容器。禁止 rejectUnauthorized=false 或跳过主机名校验。CA 公钥可分发给客户端，服务器私钥不得挂载到 Web。

必须先修复：lib/server/connectors/postgres.ts 的 normalizeUrl 当前直接删除连接串全部查询参数，会一并丢弃 sslmode / sslrootcert；分析查询与连接测试不能仅靠上述 URL 满足生产 TLS。需保留 SSL 参数，只移除 Prisma 专用参数，或显式配置 pg SSL。Prisma 与原生 pg 两条链路都要验证：正确 CA 成功、错误 CA / 主机名失败、连接在 pg_stat_ssl 中确为 TLS。

必须先补迁移：当前 prisma/ 下只有 schema.prisma，未发现 migrations；npm run db:deploy 的存在不代表具备可部署迁移。Adjust / API 落库还会运行 CREATE TABLE / CREATE INDEX，reset 分支可删除表。上线前需版本化管理 cause / data schema、表与索引，拆除生产运行时 DDL，禁止普通同步 reset。迁移进程临时以 Migration Secret 注入 DATABASE_URL，完成后销毁；不得为图省事给 Runtime DDL / DROP 权限。

5.4 数据库运行参数与生命周期

  • 在 PostgreSQL 8 GiB 容器预算内，初始建议 shared_buffers=2GB、effective_cache_size=6GB（优化器估算，不是额外分配）、work_mem=8MB、maintenance_work_mem=256MB；work_mem 按查询算子和并发放大，须结合实际压测。Compose 的 shm_size 建议 1 GiB，不使用默认小共享内存配置。
  • PGDATA 独立持久挂载，初始化启用数据校验和；保留 fsync=on、full_page_writes=on、synchronous_commit=on，不能靠关闭持久性换性能。日志设保留与轮转，慢 SQL 采集需脱敏。
  • PostgreSQL 先健康，再运行批准的迁移，成功后启动 Web 与 timer。pg_isready 只证明接受连接；应用就绪仍需验证 Runtime 账号、TLS 和所需表结构。应用发布不得重建数据库数据目录或自动执行破坏性初始化。
  • PG17 补丁更新先备份、兼容验证、安排停机窗口；跨大版本升级必须有独立 pg_upgrade 或逻辑迁移方案，不能直接换容器标签打开旧 PGDATA。主机重启应正常停止数据库，恢复后验证 WAL 恢复与应用数据。

6. 本地文件持久化与备份（不使用 S3 Bucket）

6.1 自管 PostgreSQL 与文件恢复

  • 建议每天 02:30（Asia/Shanghai）使用匹配 PG17 的原生工具做全库一致性逻辑备份：pg_dump 自定义格式覆盖 pt_ai_cause 的 cause / data schema、数据与对象；DBA 受控导出所需角色 / 授权恢复资料，并记录扩展版本、迁移版本及配置引用。备份账号经批准临时注入，不使用 Web 账号承担管理员操作，敏感恢复资料加密且仅运维可读。
  • 备份窗口暂停调度及文件写入 / 清理，保存图谱、导出、必要投递记录与清单，核对数据库文件引用；备份成功后关闭文件、完成校验与落盘，再触发数据盘快照。备份、清理和快照使用统一锁，避免正在生成或已删除的备份被标记为有效恢复点。故障时解除临时暂停并告警，不得伪报成功。
  • 本地建议保留最近两套已完成备份，云端保留最近 7 天的成功加密快照；新快照完成且包含有效备份后才能清理旧本地备份，不删除唯一成功恢复点。快照清理由获批运维自动化执行，权限按 Cause 资源标签与支持的 IAM 条件限制；Web 无创建 / 删除 / 共享快照权限。
  • 数据卷丢失时，以最近已完成快照内的有效逻辑备份作为恢复基线，而不是复制运行中的 PGDATA。由快照建立新卷，将数据库恢复到新 PGDATA，并从受控密钥系统重新交付 TLS 私钥 / Secret；上线前、重大迁移前及上线后分别按审批留存备份并做恢复演练。
  • 恢复保障变化：本版取消 S3 持续 WAL 归档方案，不再沿用旧稿“RPO ≤ 15 分钟”的目标，也不宣称具备任意时间点恢复。每日备份 / 快照的整机恢复点取决于最近成功备份的数据时间及快照完成情况；RPO / RTO 由业务审批并通过演练确认。若需分钟级恢复，另行设计符合无 S3 约束的异机备份方案，本次不默认增加主机。
  • 故障恢复流程：批准恢复资源 → 从保留卷或加密快照提取已完成备份 → 新 PG17 实例恢复角色 / 数据库与应用文件 → 验证 TLS、业务数据及文件引用 → 恢复应用 / 调度 → 更新 ALB 目标。恢复不回滚原平台 RDS，也不构成常驻第二台 Cause EC2 的申请。
  • 监控最近成功数据库 / 文件备份时间、校验结果、快照状态与有效恢复点年龄、备份占用和恢复演练结果；任务失败立即告警。数据库 WAL 正常持久性设置继续保留，但本版不要求对外归档；备份与快照验收是上线门禁，不因不使用 S3 而豁免。

  • 调度失败 / 重复投递、mock 邮件误报、图谱 / 导出备份、EBS 快照完成 / 费用及恢复点年龄、Secret 轮换与证书到期。业务指标需应用 / 脚本补采集，不是创建 Log Group 后自动具备。
  • 日志汇入 /pt-ai/prod/cause，脱敏 Cookie、Authorization、连接串、Token、原始业务内容；默认保留 30 天，审计周期由公司确定。告警复用现有 SNS / 值班渠道。
